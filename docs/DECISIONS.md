# Decisions (ADR log)

Format: context → decision → consequences / rejected alternatives. Append; never rewrite history. Supersede with a new ADR.

## ADR-001 — Monorepo layout and staged delivery (2026-06)
Stages: (1) edge agent core + tests, (2) backend FastAPI+PostgreSQL+Docker Compose, (3) dashboard React+TS, (4) RTSP field pilot. Each stage must be runnable on its own and end with `docs/STATUS.md` updated. Layout: `edge_agent/`, `backend/`, `frontend/`, `contracts/`, `docs/`.

## ADR-002 — Event contract SSOT lives in `edge_agent/edge_agent/contracts.py`
Pydantic v2 models generate `contracts/event_v1.schema.json`; a test fails if the committed file drifts. Backend (Stage 2) re-declares the same Pydantic models and MUST add a test comparing its `model_json_schema()` with the committed file. Frontend types (Stage 3) are generated from the same JSON schema. Rationale: avoid the usual multi-copy drift. Versioning: `schema_version` literal; breaking changes → `CountEventV2` + new file, never in-place edits.

## ADR-003 — Person detector: YOLOX via ONNX Runtime (licenses verified 2026-06)
Verified from official sources:
- **YOLOX** (Megvii-BaseDetection/YOLOX): code **Apache-2.0**. Official checkpoints are distributed from that repo; however GitHub issue #1865 shows an open community question about whether the weights are explicitly covered by Apache-2.0. → **Action before commercial launch:** get written confirmation or legal sign-off; fallback is training/exporting our own weights or using RT-DETR (Apache-2.0, PaddleDetection / lyuwenyu) — both fit the same `Detector` interface.
- **onnxruntime**: MIT. **opencv-python-headless**: Apache-2.0. **numpy/httpx/pydantic/PyYAML**: permissive.
- **Rejected: Ultralytics YOLOv8/YOLO11** — AGPL-3.0; Ultralytics states AGPL applies to code, architectures *and* trained weights, including edge/SaaS deployment, unless an Enterprise License is purchased. Incompatible with a closed-source subscription product without paying for the license.
- COCO-pretrained weights are trained on COCO images (CC-BY-4.0 annotations; image rights vary). This is an industry-standard risk, noted but not mitigated at pilot stage.
Weights are **not** bundled in the repo; operators export ONNX themselves per the YOLOX docs. **No accuracy has been measured for this project**.

## ADR-004 — Tracker: dependency-free IoU tracker baseline, ByteTrack later
`IouTracker` (constant-velocity prediction, greedy IoU matching, `min_hits`, `max_age`) ships as the baseline behind the `Tracker` protocol so the counter can be tested deterministically without model dependencies. Upgrade path: **ByteTrack** — original repo (ifzhang/ByteTrack) MIT; Roboflow `supervision` MIT (its built-in `sv.ByteTrack` is deprecated since 0.28 in favour of the separate `trackers` package — check that package's license before adopting). **Rejected: boxmot** (AGPL-3.0).

## ADR-005 — Counting semantics: directed line + per-track hysteresis, UNKNOWN initial side
See `docs/ARCHITECTURE.md` → "Counting semantics". Key choice: a track must first be confirmed on one side before it can ever produce a crossing, so track-loss/re-id can only undercount, never overcount. Preferred failure mode for a paying customer: missed count over phantom count. Anchor defaults to bbox bottom-center (feet) — the point that actually crosses a floor line under a typical overhead-angled camera.

## ADR-006 — Identity from authentication, never from payload
Edge payload contains `camera_id` and `line_id` strings only. `tenant_id/store_id/device_id` are resolved server-side from the device API key; `CountEventV1` uses `extra="forbid"` so a spoofed `tenant_id` field is rejected at parse time on the edge and must be rejected by the backend.

## ADR-007 — Reliability: SQLite write-ahead buffer with explicit failure
`events(event_id PK, payload, status pending|sent|rejected, attempts, created_at, sent_at, last_error)`, WAL + `synchronous=FULL`. Persist before send; mark `sent` only on server ack (`accepted` or `duplicates`); `rejected` rows are kept for inspection. Capacity applies to pending rows; when full, `append` raises `BufferFullError` and the pipeline logs `EVENT LOST` at ERROR and sets health `buffer_full`. Alternative "block the pipeline until space frees" was rejected because it silently stalls counting; explicit loss with a counter is more honest for a pilot and can be revisited (e.g., disk-based overflow).

## ADR-008 — Time: UTC everywhere in storage; store timezone for display
`event_ts` is derived from the frame time base (file: `start_ts_utc + index/fps`; RTSP: capture wall clock). Server adds `received_at`. All timestamps tz-aware UTC; `datetime.utcnow()` is banned.

## ADR-009 — Backend persistence: SQLAlchemy 2.x async + PostgreSQL; SQLite in preview
User requirement is PostgreSQL via Docker Compose on their machine. The hosted preview workspace cannot run Docker and ships MongoDB; we will **not** build on Mongo. Stage 2 uses SQLAlchemy 2.x async with a `DATABASE_URL` env var: `postgresql+asyncpg://…` in Compose, `sqlite+aiosqlite://…` in the preview. Schema identical (Alembic migrations). The current `backend/server.py` is the untouched platform template and will be replaced in Stage 2.

## ADR-010 — Device auth: per-device API key, hashed at rest, Bearer header
Pilot-appropriate. Key shown once at device creation; server stores a hash + prefix. Hashing algorithm and rotation flow to be finalized in Stage 2 via the auth integration playbook. Rejected for now: mTLS (ops burden for a pilot), JWT device tokens (adds a token-issuance flow with no pilot benefit).

## ADR-011 — Secrets only via environment; redaction in logs
`EDGE_API_KEY`, `EDGE_RTSP_URL` from env; `.env` git-ignored; `edge_agent.redact` used for URLs/Bearer tokens; CLI log formatter redacts `Bearer …`. Tests assert the API key never appears in logs.

## ADR-012 — Device key format & hashing (finalizes ADR-010, 2026-06)
Token `dk_<key_id>.<secret>` (`secrets.token_urlsafe`, 9 + 32 bytes). DB stores `key_id` (indexed, public) and `sha256(secret)` hex; lookup by `key_id`, compare with `secrets.compare_digest` against a dummy hash when the key is unknown (uniform timing). SHA-256 is appropriate because the secret is 256 random bits (not a human password) — no bcrypt/argon2 needed. Revocation = `is_active=false` (403); rotation = issue new device, switch, deactivate old. Provisioning is a CLI (`app/seed.py`), never an HTTP endpoint.

## ADR-013 — Dashboard read endpoints: open for the pilot, optional shared read key
User chose "no login for pilot". To avoid shipping a permanently open multi-tenant API, `/api/v1/stores*` accept an optional `DASHBOARD_READ_KEY` (header `X-Dashboard-Key`). Unset in the preview. Proper per-user auth with tenant scoping is P2 and must not change the response shapes in `docs/CONTRACTS.md`.

## ADR-014 — Day/hour aggregation computed in Python over an indexed UTC range
Store-local day → `[start_utc, end_utc)` via `zoneinfo`; events fetched with `ix_count_events_store_ts`; bucketed by local hour in Python. Portable across SQLite/PostgreSQL (SQLite has no `AT TIME ZONE`) and handles DST correctly. One store-day is at most thousands of rows. Revisit with SQL `date_trunc(... AT TIME ZONE ...)` or a materialized hourly table when multi-store/month views arrive.

## ADR-015 — Schema management: Alembic (async env), `AUTO_CREATE_SCHEMA` only for dev
Compose runs `alembic upgrade head` before uvicorn. Initial revision `7f0ed43c997e`. `create_all` is gated by `AUTO_CREATE_SCHEMA=true` for throwaway DBs/tests only.

## ADR-016 — Field-pilot tooling is headless and evaluation is manual-ground-truth only (2026-06)
Edge boxes have no display, so calibration is `snapshot` (grid overlay) + `preview` (line + ENTER arrow) images, not a GUI. Visual verification uses `tools/annotate` (annotated review video + events JSONL). Accuracy is computed **only** by `tools/evaluate` against a human tally CSV (per-direction greedy time matching, ±tolerance). The repo must never contain accuracy numbers that were not produced this way. `source.frame_stride` was added so CPU-bound boxes can process every Nth frame; tracker/counter frame windows are in processed frames.

## ADR-017 — Reference clip for review runs: OpenCV `vtest.avi`
Public sample from the OpenCV repo (Apache-2.0), 768×576 @ 10 fps, 795 frames, pedestrians on a plaza. Used to exercise the real YOLOX-S + IoU tracker + counter end to end. It is **not** a door scene and has **no ground-truth tally**, so its counts are agent output only, never accuracy. Not committed (8 MB); download command in `config.review.vtest.yaml`.

## ADR-018 — Dashboard authentication: local email+password (bcrypt) → short-lived HS256 JWT; tenant scoping from DB memberships (2026-06, supersedes ADR-013)
Code-review Finding 3: read endpoints were open without `DASHBOARD_READ_KEY`, one shared key otherwise, no tenant scoping, and the key shipped in the frontend bundle. User choice: a minimal, offline-capable identity: `dashboard_users` (email, bcrypt hash via the `bcrypt` package) + `tenant_memberships`, provisioned **only** by the operator CLI `python -m app.users` (no public signup; passwords via env var or prompt, never argv). `POST /api/auth/login` issues an HS256 JWT (PyJWT, `typ: "dashboard"`, `exp` required, `JWT_SECRET` ≥ 32 chars, default TTL 12 h). Every request re-loads the user's `is_active` and memberships from the DB, so the token only proves identity; authorization is server data → deactivation is immediate and UUIDs in requests are never a permission (not-permitted store → 404, indistinguishable from unknown). Device keys and user JWTs are disjoint mechanisms (`dk_` prefix vs JWT) and each is rejected by the other's dependency. Brute force: in-memory limiter, 5 failures per (IP, email) → 429 for 15 min (per process; adequate for the pilot's single API instance). **Bearer token in `localStorage`** was chosen over a cookie session because the API is served from a different origin than the dashboard in every deployment we have (preview + Compose), which would require SameSite=None cookies plus CSRF tokens; the trade-off (XSS exposure) is mitigated by the short TTL and immediate server-side revocation. `DASHBOARD_AUTH=disabled` exists for local development only and must be set explicitly; missing `JWT_SECRET` fails startup rather than opening the API. Rejected: OAuth/OIDC provider (no offline pilot), API-key-per-user (not revocable per session, no expiry), hand-rolled token signing.

## ADR-019 — Stream discontinuity resets tracking state; `tracking_session_id` on events (2026-06)
Finding 2: RTSP disconnects froze frame-based track ageing, so stale tracks (and their confirmed side) were reused after reconnect and could produce phantom crossings. Every `VideoSource` frame now carries `session_id`; `RtspVideoSource` increments it on each successful (re)connect. `CounterPipeline` resets tracker + counter track state **once per session change** (never per frame); running totals, the SQLite buffer and pending sends are untouched. Events carry an optional `tracking_session_id` (schema v1 stays backward compatible: field optional, `NULL` for older agents; committed schema, backend mirror, migration and drift tests updated together) because `track_id` is only unique within a session. Rejected: time-based track TTL alone (still allows a reconnect within TTL to reuse sides); resetting on every read failure (would also reset on transient decode errors without discontinuity).

## ADR-020 — Device heartbeat separate from visitor events; server-stamped; latest-state-only (2026-06)
Finding 4: `last_seen_at` only moved on event ingest, so a healthy device in an empty store looked dead. `POST /api/v1/devices/heartbeat` (device key auth) records `last_heartbeat_at = server now` plus `source_status`, `last_frame_age_s`, `pending_events`, `tracking_session_id`, `agent_version` on the authenticated device only. The edge `HeartbeatSender` runs in its own thread every 60 s (`backend.heartbeat_interval_s`), independent of frames and of the event sender, and never queues: a failed heartbeat is superseded by the next (bounded backoff ≤ 300 s), so nothing accumulates offline. Staleness is one definition: **3 × interval = 180 s** (documented in CONTRACTS.md, implemented in `frontend/src/lib/time.ts`). Dashboard states: `connected`, `camera_down` (agent alive, camera down), `stale`, `unknown` (never heard), `inactive`. Visitor activity (`last_event_at`) is shown separately and never implies health. `api_key_prefix` was removed from the dashboard API (support-only data).

## ADR-021 — Overflow-safe backoff shared by sender, heartbeat and RTSP reconnect (2026-06)
Finding 5: `base * 2 ** failures` overflowed to `OverflowError` after ~1024 failures and killed the retry loop. `transport/backoff.py::Backoff` caps the exponent (`min(failures-1, 60)`) **before** exponentiation, clamps to `max_s`, applies jitter `[0.5, 1.5)`, then clamps again — so `max_backoff_s` bounds the **final** delay including jitter (name and behaviour now agree; config help text updated). `reset()` after any acknowledged batch / heartbeat / successful connect. Used by `EventSender`, `HeartbeatSender` and `RtspVideoSource`. Waits go through `interruptible_wait` (0.5 s slices) so shutdown is honoured during long backoffs. Retry semantics unchanged: network/429/5xx retry, 401/403 → `auth_failed` (kept pending), mark-sent only on ack, `event_id` stable across retries.

## ADR-022 — Evaluation matching is exact one-to-one assignment (Hungarian), per direction (2026-06)
Finding 6: greedy nearest-pair matching could return fewer pairs than possible (`truth [1.0, 2.0]`, `pred [0.0, 1.1]`, tol 1.0 → 1 pair instead of 2). `tools/evaluate.py` now solves, per direction, a padded square assignment with infeasible cost `BIG = (n+m+1)·tol + 1`, which makes "maximise pairs within tolerance" dominate "minimise total |Δt|"; ties are deterministic by sorted input order. O(k³) with k = max(n, m) — fine for pilot sessions (hundreds of events), documented as unsuitable for month-long logs. Tolerance must be finite and ≥ 0; non-finite/negative timestamps are rejected. Tests compare against an exhaustive oracle on small random cases. Precision/recall/false-positive/missed/count-error definitions unchanged.

## ADR-023 — Counting on the finite segment, not the infinite line (2026-06, refines ADR-005)
Finding 1: side changes were evaluated against the infinite line, so people passing beyond a door's endpoints were counted. A confirmed side change is now a crossing only if the recorded path (last point on the old side → deadband points → confirmation points, capped at 64 points) intersects the finite segment a→b. Endpoint tolerance `SEGMENT_EPS = 1e-9` (touching an endpoint **counts**; beyond it does not). Walking around an endpoint updates the confirmed side silently (no event), so a later real crossing is still counted correctly; exit→re-enter still yields two events. Hysteresis and multi-frame confirmation are unchanged. Rejected: checking only the confirmation point (misses diagonal walkers who cross the segment and drift sideways) and widening the segment (would re-introduce the bug at the margins).

## ADR-024 — Self-service management with three roles; device keys shown once (2026-06)
**Context.** Provisioning tenants/stores/devices/users existed only as operator CLIs (`app.seed`, `app.users`); the biggest usability gap named by the product owner. **Decision.** (1) Roles: `dashboard_users.is_platform_admin` (all tenants; seeded from `ADMIN_EMAIL`/`ADMIN_PASSWORD`, idempotent, password re-synced at startup) and `tenant_memberships.role ∈ {owner, staff}` (`viewer` migrated to `staff`). Staff is strictly read-only. (2) Write endpoints under `/api/v1` (`docs/CONTRACTS.md` → Management); authorization is resolved from the DB row's `tenant_id` and the caller's memberships on every request — never from IDs in the body. Not-visible → 404 (indistinguishable from non-existent), visible-but-staff → 403. (3) Device API keys are returned exactly once on create/rotate (`api_key_show_once`); rotation invalidates the old key immediately. (4) Cameras with count events cannot be deleted (409) to keep history intact. (5) Owner-created users are tenant members; a user may belong to several tenants with different roles. **Rejected.** Public signup (no — B2B, operator/owner invites); cookie sessions (kept Bearer JWT from ADR-018 to avoid a CORS/credentials change in this stage); soft-delete for stores (no delete at all in this stage; deactivate devices instead). **Consequences.** CLI tools remain for bootstrap; UI page `/pengaturan`. Frontend sessions written before this ADR lack `memberships` and are refreshed once via `/api/auth/me`.

## ADR-025 — Range reports computed server-side in the store timezone; comparison = preceding equal-length period (2026-06)
**Context.** Phase 2 of `docs/ROADMAP.md`: owners need trends beyond a single day, a comparison, busiest hours, CSV export and one table for all stores. **Decision.** One endpoint `GET /stores/{id}/report?from&to` returns zero-filled daily buckets, the same totals for the immediately preceding period of equal length, and a 24-slot hour-of-day profile summed over the range; range capped at 92 days. `GET /overview` returns one row per permitted store with today / yesterday / 7-day mean / device problems, each in the store's own timezone. Bucketing is done in Python over the `(store_id, event_ts)` index — identical semantics to the existing day/hour endpoints (ADR-008) and portable across SQLite/PostgreSQL. CSV is generated in the browser from `daily` (no auth-header issue with `<a download>`, no second server format). **Rejected.** SQL `date_trunc` (dialect-specific, tz handling differs between SQLite and PostgreSQL); "same period last year" (pilot has no such history yet — trivially addable as a query param later); pre-aggregated daily tables (premature at pilot volumes; revisit when a store exceeds ~10⁵ events/month). **Consequences.** Report cost is O(events in range); the 92-day cap bounds it. Percent change is `null` when the previous period is 0 (UI shows "—", never a fake 100 %).

## ADR-026 — Store opening hours filter reports and device-problem flags, not the raw day view (2026-06)
**Context.** Owners asked that reports and alerts ignore closed hours (cleaners at night, camera restarts before opening). **Decision.** `stores.open_time/close_time` (`HH:MM`, store-local, both NULL = 24 h, `close <= open` wraps midnight). `/report` and `/overview` count only events inside the window and `/report` states how many were excluded (`outside_hours_excluded`) so the filter is never silent. `/overview.devices_problem` is 0 while the store is closed (and `is_open_now` is exposed); future alert rules (Phase 3) must reuse `app/hours.py::is_open_at`. The single-day dashboard (`/summary`, `/hourly`) stays unfiltered — it is the raw truth for debugging. **Rejected.** Per-weekday schedules (not requested; the model can grow to a JSON schedule later without changing the API shape), deleting out-of-hours events (never delete count data), filtering at the edge (edge has no notion of business hours; server-side keeps it editable).

## ADR-027 — Heartbeat history stored raw for 7 days; timeline segments computed on read (2026-06)
**Context.** "Why was the camera down yesterday?" cannot be answered from the latest heartbeat alone. **Decision.** Append every heartbeat to `device_heartbeats` (~1 440 rows/device/day at 60 s) and prune to 7 days per device on insert — no scheduler needed. `GET /devices/{id}/heartbeats` turns samples into merged segments (`connected | camera_down | stale | unknown`) with the same 180 s stale threshold as the live status, so history and current badge never disagree. Pure function `build_segments` is unit-tested. **Rejected.** Storing only state transitions (loses `pending_events`/frame-age context and needs care around restarts), a separate aggregation job (premature), longer retention (revisit with PostgreSQL partitioning if a customer needs it).
